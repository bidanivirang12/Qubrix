# Security controls

Controls below are design requirements. "How tested" describes verification to implement and run; it is not a claim that those tests already exist or pass.

| ID | Control | Where enforced | How tested |
|---|---|---|---|
| C-01 | Validate OIDC JWT signature against configured issuer JWKS and enforce issuer, audience, expiry/not-before, and accepted signing algorithm; fail closed on invalid/unknown key or unavailable metadata. | Authentication dependency at API boundary | Unit tests for valid and invalid claims, wrong issuer/audience, expiration, unknown `kid`, disallowed algorithm, JWKS refresh and outage; HTTP tests assert protected routes reject unauthenticated calls. |
| C-02 | Build immutable organization, actor, roles, and scopes only from verified identity claims. Ignore/reject client attempts to provide these fields. | Identity context and request schema | API tests submit forged tenant/actor/role fields and verify they cannot change context or privilege. |
| C-03 | Require route-specific role and scope, then enforce object-level organization ownership on every lookup and mutation. | Authorization dependency and repository/query layer | Parameterized cross-tenant tests for every object route, including guessed IDs, list filters, and mutations; deny-by-default role/scope matrix tests. |
| C-04 | Put `organization_id` on tenant-owned rows, use tenant-scoped foreign keys and composite unique constraints, and include organization scope in reads and writes. | SQLAlchemy repositories and PostgreSQL schema | Migration/schema tests inspect constraints; integration tests prove cross-tenant references and duplicate identities are rejected. |
| C-05 | Validate event type/schema and size; accept only event fields needed for processing; do not accept client-set organization, receipt time, verification, score, decision, or finding state. | Pydantic request schemas and ingestion service | Schema/API tests reject forbidden fields, unsupported event types, malformed timestamps and oversized inputs; assert `organization_id` and `received_at` are server assigned. |
| C-06 | Use vetted cryptographic libraries and a narrow key-provider interface; private keys stay in KMS/HSM; algorithm choice is explicit and unsupported algorithms fail closed. | EncryptPlus verifier and provider adapter | Provider contract tests for success, invalid signature, missing key, outage, unsupported algorithm, and no fallback; inspect persisted rows/log captures/responses for key bytes. |
| C-07 | Persist verification status as a risk input; invalid, unknown-key, and unavailable verification each create an independent security finding. Valid signatures never reduce risk. | Verification, findings, and risk transaction | Risk tests vary signature validity while holding other inputs fixed; assert valid does not lower score, and each failure status creates its own durable finding and required decision floor. |
| C-08 | Detect signed-event replay using tenant-scoped, unique replay identity/nonce; replay forces `FLAG` regardless of score or signature validity. | Ingestion transaction and database uniqueness | Concurrent integration tests submit duplicate replay identities with differing HTTP idempotency keys; assert one detection and a replay finding with `FLAG`. |
| C-09 | Scope idempotency by organization, actor, operation, and key; identical canonical request returns original committed result, changed request returns 409. | Ingestion idempotency record and PostgreSQL uniqueness | API and concurrency tests for same key/same request, same key/different request, simultaneous requests, rollback, and tenant/actor isolation. |
| C-10 | Rate-limit authenticated requests by organization and principal/route using atomic database-backed budgets; fail closed for protected writes if the limiter cannot enforce a budget. | API middleware/dependency and PostgreSQL | Integration tests for threshold, window reset, concurrent increments, tenant isolation, 429 `Retry-After`, and database outage on writes. |
| C-11 | Use least-privilege roles/scopes and service identities; ADMIN has no decrypt permission by default. Never expose a generic secret-export or decrypt endpoint. | Permission matrix, route declarations, provider interface | Route inventory test verifies every endpoint declares role/scope; role matrix tests prove ADMIN decrypt denied and only explicit permitted operations succeed. |
| C-12 | Bound request size and parsing/cryptographic work; use parameterized SQL and allowlisted fields; return generic validation errors without echoing sensitive input. | Ingress, Pydantic schemas, database access | Tests for oversized/malformed bodies, unknown fields, SQL-like input, and error-body non-echo; fuzz/property tests for parsers where implemented. |
| C-13 | Never persist/log/respond with secret keys, full card numbers, or plaintext sensitive payloads; log identifiers and redacted reason codes only. | Schema, persistence, response serializers, logging and tracing | Canary-value tests inspect captured logs, API responses, and database records; source/config scans for accidental secrets; review production log fields. |
| C-14 | Record append-only audit facts for security-sensitive key lifecycle, authorization-sensitive changes, and event/finding actions; restrict audit reads and preserve actor attribution from identity. | Audit service, database and audit routes | Integration tests assert audit records commit with changes and cannot be silently modified/deleted by application role; authorization and redaction tests. |
| C-15 | Pin dependencies with uv lockfile, review dependency updates, and run reproducible tests/static checks in CI. | Dependency manifests and GitHub Actions | CI checks locked sync, tests, Ruff, pyright, migration checks; dependency review/scan results must be reviewed before release. |
| C-16 | Build and scan container images in CI because Docker is unavailable locally; deploy only reviewed artifacts and keep build credentials out of logs/artifacts. | GitHub Actions and deployment pipeline | CI build and container-scan jobs; inspect run results and artifact provenance. Local status remains unverified until those jobs execute. |

## Decision invariants

- Tenant, actor, and roles come from authenticated identity, never request bodies.
- A valid signature is not proof of transaction legitimacy and must not lower a risk score.
- Invalid, unknown-key, or unavailable verification must not be silently treated as valid; each failed/unavailable verification has its own finding.
- Replay forces `FLAG`. Invalid and unknown-key verification impose at least `VERIFY`.
- No silent algorithm downgrade; no home-grown cryptographic primitives.
- No secret keys in source, database, logs, or responses; no full card numbers or plaintext sensitive payloads in storage.
