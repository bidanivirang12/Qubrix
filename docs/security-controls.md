# Security controls

Controls below distinguish planned controls from controls implemented in Phase 3A-1. The authentication and principal controls added for this phase have concrete test paths; only report them as locally verified after those tests have passed. Remaining rows are design requirements until implementation and testing.

## Decision invariants

- Tenant, actor, roles, and scopes come from validated identity (`organization_id`, `sub`, `roles`, `scope`), never request bodies.
- A valid signature is not proof of transaction legitimacy and must not lower risk.
- Disabled/revoked keys cannot be `VALID`; every non-VALID verification outcome has its own finding.
- Replay forces `FLAG`; invalid and unknown-key verification impose at least `VERIFY`.
- No silent algorithm downgrade; no home-grown cryptographic primitives.
- No PAN, plaintext identity, secret key, signature, or plaintext sensitive payload is stored/logged. Explicit encrypt/decrypt API bytes are transient only; decrypt is service-only.
- `KEY_LIFECYCLE_CHANGE` event ingestion records a report; it does not mutate key state.
